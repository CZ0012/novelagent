# Agent Runtime Contract v1

## Purpose and scope

This additive contract governs workspace-local provider settings, reusable writing
System prompt presets, model discovery, and exact Draft continuation. It does not
change Graph Store canon, review permissions, project language, or Draft schemas.
Related contracts: `language_policy_v1`, `context_pack_v1`,
`proposal_artifact_v1`, `workflow_run_v1`, and `source_document_v1`.

## Settings and preset routes

- `GET /settings/agent` returns the existing redacted provider settings plus
  `selected_preset_id` and `agent_presets`.
- `PUT /settings/agent` preserves every omitted setting, including credentials,
  the selected preset, and custom presets. Existing full requests remain valid.
  A supplied `selected_preset_id` must exist; invalid selections return `422`
  before persistence or live configuration changes. Only explicit `clear_api_key`
  or a supplied replacement key changes credentials.
- `POST /settings/agent/presets` creates a custom preset.
- `PUT /settings/agent/presets/{preset_id}` replaces its editable fields.
- `DELETE /settings/agent/presets/{preset_id}` deletes a custom preset.

Preset writes return the same full redacted settings response. Create and edit
accept `{name, description?, system_prompt}`. A preset response is
`{id, name, description, system_prompt, builtin}`. Names and prompts are stripped
and non-empty; name length is at most 80 characters, description at most 500,
and System prompt at most 12000. At most 100 custom presets may be stored.
Custom IDs are generated by the server with `custom_` prefix. Callers cannot
override IDs or mark custom data as built-in.

Built-ins are `builtin_zh_concise` (default), `builtin_balanced`, and
`builtin_en_precise`. The first instructs Chinese writing to use fewer adverbial
phrases and more precise actions and dialogue. All presets defer to project
language. Built-in names/descriptions may be presented using separately loaded
UI translations keyed by their stable IDs; custom names and System prompt
content must never be silently translated. Built-ins are immutable (`409`).
Unknown custom IDs return `404`. Deleting the selected custom preset resets
selection to `builtin_zh_concise`; deleting an inactive one preserves selection.

Preset CRUD requires at least `read_generate`. Provider settings, selection,
and the existing permission-level control remain local author self-service;
changing those settings does not grant a story-store write outside its existing
permission gates. Presets themselves never mutate story stores. Settings writes
are serialized within one API process and atomically replace local
`agent_config.json`; persistence must succeed before the live configuration
changes. Multiple independent servers writing one workspace are unsupported.
Existing settings files without preset fields load the default built-in and an
empty custom list. Invalid persisted selections fail validation.

CLI runtime construction loads the same saved provider and preset configuration.
The CLI remains a direct local-author interface; API permission controls govern
API actions and do not constitute operating-system access control on workspace
files or CLI commands.

## Application and provenance

At construction a creative service freezes a copy of its selected preset. Scene
generation, generated Proposal revisions, and Agent discussion/revision/
continuation include its text in an additional System message after the base
task contract. Mandatory canon, human review, source trust, scope, JSON format,
POV and knowledge constraints are restated, and the authoritative project
language message follows the preferences. Presets are preferences, not authority
to override these boundaries. Fact extraction, structure extraction and
continuity checks do not receive creative presets. Rule-based generation does
not pretend to execute System prompt instructions.

Agent discussion responses add `agent_preset: {id, sha256}`. Generated Proposal
provenance uses a compact `agent_preset=<id>; sha256=<digest>` marker in the
existing `note` field. Scene-generation workflow `write_draft.artifact_refs`
may include `agent_preset_id` and `agent_preset_sha256`. SHA256 hashes the exact
UTF-8 System prompt. Editing a preset keeps its stable ID and changes its hash;
historical markers remain unchanged. Full prompts and credentials are not
copied into story provenance. These markers identify the applied instruction
version; they are not a full historical prompt archive. Standalone Draft
responses retain their existing schema.

## Exact continuation

`POST /projects/{project_id}/scenes/{scene_id}/agent-discussion` adds
`mode = continue_scene`. This new mode requires `include_latest_draft = true`
and explicit `included_draft_id`; omission is `422`. The server resolves that
exact same-project, same-scene saved Draft before provider use; missing or
out-of-scope IDs return the existing uniform `404`. Newer Drafts never replace
the pinned baseline. A supplied `base_text` must exactly match it. The original
Draft must contain text and have the authoritative output language.

The model returns a non-empty `continuation_text` in addition to `reply` and
`proposal_title`. This new field is validated against project language before
any Proposal is saved. The model receives a bounded ending excerpt (currently
12000 characters) of a long Draft, marked `base_text_excerpt = tail` and
`base_text_truncated = true`; revision/discussion payloads retain leading
excerpts. The persisted full Draft is never truncated. Source selection,
cross-language checks and source truncation remain governed by their contracts.

The server constructs the Proposal body by retaining the complete exact Draft
as a byte-for-byte string prefix, adding paragraph separation if needed, and
appending the validated continuation. It saves a new non-canon `scene_draft`
Proposal with a unique exact Draft source ref and the current scene target.
`replacement_applied` is false. The original Draft, Graph Store, Event Log and
Candidate Store are unchanged. Accepting or promoting this Proposal still
requires existing explicit review and promotion actions.

## Generic provider discovery and safe errors

`GET /settings/agent/models` requires `read_generate`, uses the configured
provider's authenticated `GET /models` protocol with at most a 15-second
timeout, and returns
`{models: [{id}], current_model, current_model_available, status, error}`.
On a valid bounded listing, `status = ok` and availability is an exact ID match.
The list is deduplicated and contains at most 1000 IDs of at most 200 characters.
On unsupported or failed discovery, `status = unavailable`, models is empty,
availability is null, and error is safe diagnostic text. Model discovery never
changes the configured identifier. A missing identifier is reported honestly;
manual models remain supported when a provider does not implement discovery.
Successful discovery verifies listing connectivity, not generation capability
or any provider/model provenance claim.

Provider HTTP diagnostics include status plus stable categories such as
`invalid_credentials`, `rate_limit`, `endpoint_not_found`, `invalid_request`,
or `provider_unavailable`. Transport and malformed responses use
`connection_error` or `invalid_response`. Arbitrary provider error bodies,
network reasons, credentials, and manuscript text must not appear in UI errors
or persisted workflow failure messages. Successful generation continues to use
the configured generic Chat Completions-compatible endpoint and exact model ID.

## Empty scene drafting and exact selected passages

`agent-discussion` adds `mode=create_scene` for an empty existing Scene. It uses
the configured provider, selected preset, authoritative project language and the
same explicitly selected context/reference policy as other modes. Missing scene
planning fields may remain explicit Context Pack gaps. The model must return
actual scene prose in `proposal_body`; only a non-canon `scene_draft` Proposal is
created. A nonempty current saved Draft rejects the operation before provider use.
The server records the generation-time empty-scene baseline as described in
`proposal_artifact_v1`; acceptance plus separate guarded promotion is required.

Optional paired `selected_start` / `selected_end` are half-open UTF-16 offsets
into the exact `included_draft_id`. Their use requires that pinned Draft ID and
`selected_text`. The server verifies scope, Unicode boundaries and exact text
before contacting the provider. It preserves whitespace and splices only that
specific occurrence, so repeated identical paragraphs remain independently
selectable. Draft source refs record offsets, `offset_unit=utf16` and selected-text
SHA-256. Requests without offsets retain the legacy unique-text replacement and
ambiguity fallback. Generated text and UI selection/diff state never mutate canon.

Project-level `composition-proposals` follows the separate bounded schema and
review/apply path in `proposal_artifact_v1`. Its full explicit source and Draft
inputs are rejected if too large rather than silently clipped.
